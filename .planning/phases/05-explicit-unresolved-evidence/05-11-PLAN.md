## Flagged assumptions

- Revision 2 split this plan out of 05-09 (checker scope warning): 05-09 keeps the change record, the ledger tails, and the history sequences; this plan holds search sync, the external real-path lifecycle proofs, the cross-repository search proof, and the benchmark. It touches the same tail files as 05-09, so it runs one wave later.
- Search sync happens after the ledger at each settle point (order does not matter: the two writes are independent, and both use the IDs drained once before the ledger). The cold `TrackRepoCtx` tail reaches search sync through `reconcileCobolRepos` (05-09 revision 3). The cold path rebuilds FTS for the tracked repository (`populateSymbolFTS`) before that tail, so the sync there matters for dependent repositories and, on the shadow path, for the tracked repository's own shadow-built placeholder and finding that the tail's master evicts: their IDs are in both drained lists (added by the tracked indexer's shadow resolve, evicted by the master), so they are deleted from search and not re-upserted. Re-upserting a tracked-repository node is idempotent.
- Revision 3 (checker warning, fallback masters): `runMasterResolveHookedContext` drains its master after `ResolveAllContext` returns, whatever the error (a reconcile that ran before a cancellation still changed the store), and passes only the added and evicted IDs to `syncCobolFindingFTSByRepo`; the drained repository set is dropped and no ledger runs there, so the 05-09 ledger sites stay exactly two. History is a state-based diff (05-09 flagged assumption): where `reconcileCobolRepos` follows the master (the incremental fallback, incremental_watcher_batch.go:437) it recomputes the same widened set and records the transitions at that step; after the deferred-mutation full fallback (multi.go:902, reached from `FinishTailResult` after enrichment) and `RunPreEnrichResolve` (multi.go:1139), both of which run after the batch reconcile has already decided the same COBOL candidates, any residual transition is recorded at the repository's next settle point (D-07 best effort), as before this plan. This is the smallest change that covers all three fallback callers in one place: no new `MultiIndexer` field, no pending-ID set, no extra lock. `runMasterResolveFiles` and `runMasterResolveNames` call neither `ResolveAll` nor `ReconcileCobol`, so they need no drain. `TestCobolFindings_SearchAfterFallbackMasterResolve` calls `runMasterResolve` directly (the exact call of the incremental fallback, incremental_watcher_batch.go:413) after an interrupted reindex, because the "needed, no frontier files" branch has no deterministic real-path trigger; the deferred-mutation full fallback (multi.go:902) and `RunPreEnrichResolve` (multi.go:1139) run the same function.
- `syncCobolFindingFTS` mirrors the incremental stage path's search writes exactly (`deleteSymbolFTS`, `SymbolFTSBatchUpserter` with `ftsTokensFor`, `shouldIndexForSearch`) and invents no new index; an ID in both lists (added then evicted, or the reverse, between two drains) is deleted and then upserted only if its node still exists, which leaves the correct final state.
- `syncCobolFindingFTSByRepo` and the per-repository write path are kept separate because the standalone tail has one `Indexer` and the MultiIndexer tails must route each ID to its own repository's `Indexer` (each holds its own `projectName` for tokens); IDs whose prefix is empty or untracked are skipped, per the `RepoPrefixOfID` doc.
- The cold-track search case asserts removal (fdepb's placeholder and finding leave search when fdepa is tracked) and absence (tracking fdepb after fdepa leaves neither searchable), each with the shadow off and on; a cold track can only add candidates, so it adds dependent-repository findings only in edge cases (for example the first scope-wide pass after the `/6` re-extraction), which the same per-prefix upsert covers.
