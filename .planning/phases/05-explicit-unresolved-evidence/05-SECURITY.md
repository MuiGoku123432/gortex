## Trust Boundaries

| Boundary | Description | Data Crossing |
|----------|-------------|---------------|
| Repository COBOL source to extractor and resolver (05-01, 05-13) | Untrusted, repository-controlled text decides gap positions, references, and evidence bytes. | Estate source text (sensitive). Only digests and ranges may cross into findings. |
| Producer handoff to graph (05-03, 05-07, 05-10) | Grade reasons are copied, never re-derived. Recovery cascades must surface. Producer error text must not reach Meta. | Producer reason vocabulary (low). Analysis error text (must not cross). |
| Extractor stamps to resolver decisions (05-10) | Edge reasons decide whether a finding claims "not obtained". | Edge reasons and binding keys (low). |
| Caller repository to allowed and dependent repositories (05-05, 05-09, 05-11) | Binding and placeholders respect the per-caller scope. One repository's reconcile re-decides and writes nodes owned by every repository whose `resolve_from` names it. | Candidate sets, policies, and dependent repositories' findings and placeholders. |
| Resolver to store eviction (05-02, 05-05, 05-08, 05-15, 05-16) | Resolver-computed ID lists create and evict nodes the resolver does not own by file. A wrong or crafted list must not remove other kinds or generations. | Node ID lists (integrity-critical). |
| Repository content and tracked prefixes to the graph ID namespace (05-16) | Repository paths, program names, literals, and user-chosen repository prefixes decide node IDs. Placeholders must not share that namespace. | Node IDs (integrity-critical). |
| Placeholder IDs to ID-only consumers (05-16) | `graph.RepoPrefixOfID` callers must not route a placeholder into another repository's data. | Derived repository prefixes. |
| Shadow graph to durable store and search index (05-09, 05-11) | Cold indexing resolves on an in-memory shadow that holds only the tracked repository and keeps no history. | Shadow-built nodes, binding decisions, and FTS rows. |
| Resolver changes and indexer tails to durable store and search index (05-06, 05-08, 05-09, 05-11) | Transitions and FTS rows are derived from graph state at settle points. Missing pairing keys would merge ledger groups. | Finding IDs, statuses, digests, stamps, and FTS rows. |
| Concurrent callers to the shared SQLite store (05-14) | MCP track, file watchers, batch transitions, and daemon warmup mutate findings and read them for the ledger. | Finding nodes and `finding_history` rows (lineage). |
| SQLite store to MCP/CLI sessions (05-01, 05-04, 05-12) | Findings, placeholders, and `index_health` counts are served to sessions of a resolved repository scope. | Finding Meta (digests, ranges) and integer counts. |
| SQLite snapshot to Neo4j projection (05-04, 05-17) | Finding Meta leaves the authoritative store. Projection holders can hash guesses against stored digests. | Finding Meta and evidence digests. |
| Finding state to future code (05-12, 05-14) | Later phases (MCP tools, AI review, claims) cite findings and history but must gain no write path. | Finding status and `finding_history` lineage. |
| User documentation to operators (05-17) | Operators rely on the docs to judge what finding IDs and history reveal and guarantee. | Disclosure statements. |
| Test run to the local volume (05-17) | The full race suite writes large temporary data on a nearly full disk. | Disk capacity. |
