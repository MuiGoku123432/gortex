## Flagged assumptions

- Discretion (RESEARCH Open Question 1): the ledger runs at the indexer level on the durable store, never inside `reconcileCobol`. The standalone `Indexer.Index` cold path (no MultiIndexer) has no ledger tail; its first transitions are recorded at the next mutation tail (D-07 best effort: history is a log of observed transitions, not canonical state).
- Revision 2 (checker blocker, D-03 across repositories): one settle point can add or evict findings and placeholders outside the repository that changed, because `cobolReconcileRepos` widens the reconcile set to every repository whose `resolve_from` names a changed one, and a per-repository cold `ResolveAll` reconciles every COBOL edge (scope nil). A ledger over only the changed repository would leave a dependent repository's closure unrecorded, and that repository's next pass could pair the gone finding with an unrelated new one in the same container (a false `superseded`). So each settle point drains first and ledgers own ∪ reconciled ∪ tracked ID prefixes. The reconciled set covers the case where an earlier pass on a discarded master (the `runMasterResolve` fallback) did the work and the tail's own pass changed nothing, since that pass recomputes the same widened set; the ID prefixes cover the scope-nil per-repository pass. The standalone tail passes `tracked` nil (ID prefixes ignored), because an unprefixed indexer's IDs begin with a path segment; its own prefix (or `""`) plus the reconciled set covers a single-repository graph.
- Discretion (change record): an additive drain accessor, not a new return value on the exported `ReconcileCobol` (2 production and about 35 test callers stay unchanged). It accumulates sets until drained instead of overwriting per pass, because the standalone fallback runs `ResolveAll`'s settle-window reconcile and then `ReconcileCobol` before one drain, and an overwrite would let the no-op second pass hide the first pass's changes. Its own leaf mutex means draining a per-repository resolver from `reconcileCobolRepos` never waits on that repository's running resolve. Bounded growth: every resolver that outlives a pass is drained at its repository's next settle point (the standalone tail; `reconcileCobolRepos`, which drains the per-repository resolver of every repository in its base set and so covers the cold-track tail, a warm-restart full retrack, and `EndBatch`); master resolvers are discarded after the call (05-11 drains the master of every `ResolveAll` into search sync before discarding it).
- `recordCobolFindingLedger` in `reconcileCobolRepos` uses `mi.RepoPrefixes()` as its base when `repos` is empty; the standalone tail uses `idx.repoPrefix` (possibly empty, which is a valid sidecar key). It returns the drained added and evicted IDs; this plan's callers discard them and 05-11 syncs search from them.
- Batch deferral (corrected in revision 1): `EndBatch` and `ResetBatch` reconcile only `mi.batchCobolRepos` (multi.go:1606-1616, 1641-1652), which before this plan only the warm-restart deferral filled (multi.go:3441-3447); a cold `TrackRepoCtx` under `deferResolve` would otherwise never get a reconcile or ledger pass. So the deferred `TrackRepoCtx` adds its repository to `mi.batchCobolRepos`, checking `mi.deferResolve` and inserting in the same `mi.mu` critical section (EndBatch clears the flag and detaches the set under the same lock, so a repository is either consumed by that EndBatch or tracked after it with an inline tail). The extra `reconcileCobolRepos` for a COBOL-free repository is the existing early return plus an empty ledger read.
- Revision 3 (checker blocker, GAP-02 and D-03 on the cold shadow path): a runtime cold track outside a batch (track_repository -> checkout_lifecycle.go:461 -> `TrackRepoCtx`) takes the shadow under the defaults, and its resolve sees only the tracked repository. A tail that only drained the tracked indexer's resolver and ran the ledger would (a) persist and record a not-obtained placeholder and `EXTERNAL_UNRESOLVED` finding for a `CALL` whose target a `resolve_from` repository already holds (a false finding, 05-08 T-05-39), and (b) leave a dependent repository's finding open when the tracked repository supplies its target, until that repository's next COBOL mutation or a daemon restart. The non-deferred tail therefore calls `mi.reconcileCobolRepos({repo})`, exactly the warm-restart shape: the master runs on the durable store with every tracked repository's candidates and policies, widens to dependent repositories, re-binds the edge (evicting the fabricated finding and sweeping the placeholder, 05-05/05-08), drains itself and the tracked indexer's resolver, and ledgers; the ledger is a state-based diff, so a finding created and evicted before the tail's ledger never gets a row. The same tail closes the race in which `EndBatch` clears `deferResolve` between a deferred track and its tail: the inline tail's master decides the repository's COBOL edges itself before its ledger, whichever of it and `EndBatch`'s master runs first. Every harness disables the shadow (`newCobolLifecycleEnv`), so `TestCobolFindings_HistoryDependentRepo` runs both cold-track orders with the shadow off and on, and the `shadow=on` subtest proves the shadow ran (admissions counter delta). Cost: one master COBOL reconcile per cold track outside a batch, the same cost the warm-restart path already pays per repository; batched tracks still pay it once at `EndBatch`. A shadow-built placeholder or finding exists in the store only between the shadow drain and the tail of the same `TrackRepoCtx` call.
- Scale: `recordFindingLedger` reads `LatestFindingTransitions` (05-06), so each pass costs O(active findings + findings ever recorded) rows read once, not O(history). The first pass after v23 appends one open row per active finding (per-token tails, D-18) in one write transaction; 05-11's `BenchmarkRecordFindingLedger_LargeRepo` measures both passes and its SUMMARY records the numbers.
