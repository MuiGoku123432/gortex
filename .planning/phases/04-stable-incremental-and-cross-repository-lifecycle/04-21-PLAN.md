<objective>
Close the topology-change half of VERIFICATION `gaps[1]` (review WR-01 and WR-02). After plan 04-20, pruning follows the live set of repositories. But a repository the outer one already indexed keeps its stale state until something reindexes it:
- Tracking a nested repository later leaves the outer repository's `alpha/nested/...` copies in place. Its watcher then refuses their updates and deletes.
- Untracking a nested repository leaves those files out of the outer graph.

Either way, incremental differs from a clean build of the same final inputs (SC-4, ID-09), and in the track-later case one file has two owners (SEC-08).

This plan reconciles the enclosing repository's subtree at the moment the topology changes. It reuses `IncrementalReindexRepo(outer, [nestedRoot])`, the existing scoped reconcile:
- On track, the walk now prunes the nested root, and the scoped deletion pass purges the present-but-excluded copies.
- On untrack, the walk admits the subtree.

One private helper serves both directions. It runs only after the triggering operation has released every lock and lane, and never inside a repository topology batch.

## Gap closed

VERIFICATION `gaps[1]` `missing` item 2: "On untrack of a nested root, reindex (or admit) the enclosing repository's subtree. On track of a nested root, evict the enclosing repository's file nodes under it." Also item 3: "untrack beta, then alpha's incremental pass equals a clean alpha-only dump; track beta later, then alpha/nested is evicted without a manual IndexRepo". Plan 04-20 closed item 1 and the projects: and inactive-entry tests.

Design (decided here, justified):
- **One existing reconcile, both directions.** `IncrementalReindexRepo(outer, [nestedRoot])` already does both jobs. With the nested root registered, the scoped walk prunes it and the deletion pass purges the outer repository's copies. With it untracked, the walk admits the subtree. No new eviction code, no new lane logic.
- **Run after, never inside.** The reconcile takes the outer repository's lane and the topology writer itself. It is called only after the track or untrack has returned: TrackRepoCtx after trackRepoSourceCtx, and untrackRepoChecked after its teardown, whose defers hold the batch gate and topology writer. This is the lane-ordering issue 04-18 deferred. Running the reconcile as a separate step means no nested lane is ever acquired.
- **Skip inside a topology batch.** The daemon warmup holds `batchMutationGate.Lock()` across its pool, so an unmarked IncrementalReindexRepo there would deadlock. Warmup convergence comes from 04-20's declared roots and the outer repository's census instead.
- **Skip the no-op track case.** On track, an enclosing repository is reconciled only when its committed FileMtimes holds a key under the nested root. This covers every tracked worktree under a builtin-excluded `.claude/` and every warmup where pruning already happened. Untrack has no such guard, because admission is the point.
- **untrackRepoChecked becomes a thin wrapper.** The existing body is renamed `untrackRepoTeardown`; only the function name changes. The new `untrackRepoChecked` captures the root under mi.mu.RLock (from mi.repos, or from the pending-untrack state on a retry), calls the teardown, and admits on success. All three public paths, UntrackRepo, UntrackRepoChecked and purgeRepoChecked (the lifecycle saga), inherit it with one hook.
- **ReconcileRepoCtx stays without the hook.** It is the warmup-only registration path, and the warmup converges as above. That leaves one public path that registers a nested repository while the outer one still holds copies. The MCP fixture uses it to keep testing the physical-owner gate in that window.
